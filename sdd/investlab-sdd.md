## 1. Введение
### 1.1 Назначение документа
SDD фиксирует **как** предполагается построить InvestLab на основе SRS версии 0.2 из ЛР №3 с учётом изменений ЛР №4. Адресаты — разработчик, заказчик и преподаватель. Описание является проектным решением и не подтверждает завершённость каждой функции.

### 1.2 Область применения
Локальная desktop-система для macOS на C++ и Qt6 Widgets с получением исторических котировок и моделированием Buy & Hold, DCA, SMA, RSI по согласованному плану. Портфели и история симуляций — в SQLite. Приложение не размещает торговые заявки и не требует брокерского счёта. Текущий релизный охват: Все базовые функции, включая RSI, в исходном объёме (F01–F10, 68 дней). 

### 1.3 Определения
SRS — требования к ПО; SDD — описание проектирования; ADR — обоснование решения; MVP — первая поставляемая версия; API — внешний источник котировок; DCA — регулярные взносы; SMA/RSI — технические индикаторы; Qt6 — GUI-фреймворк; SQLite — локальная реляционная БД.

## 2. Обзор дизайна
### 2.1 Задачи стейкхолдеров
- **Пользователь:** понятный выбор активов, воспроизводимые результаты, отсутствие реальных сделок.
- **Заказчик:** приоритетные функции в пределах срока и стоимости, возможность согласовать изменения.
- **Разработчик:** модульность, однозначные правила исполнения стратегий, тестируемость и локальное хранение.
- **Преподаватель:** трассируемость SRS → SDD → ADR → план и история обсуждения в PR.

### 2.2 Выбранные точки зрения
Применены **Context** (границы/акторы), **Composition / Logical** (компоненты и ответственности), **Information** (сущности данных), **Interface / Interaction** (обмен сообщениями, ошибки), **Algorithm** (стратегии), **Deployment** (macOS и SQLite), **Resources** (оценка итераций). Для небольшой desktop-системы самостоятельные физические сети, распределённый параллелизм и серверная инфраструктура неприменимы.

## 3. Проектные представления
- **DV-01 / Context:** пользователь → Qt6 GUI → движок моделирования; внешние котировки поступают через MarketData, результаты сохраняются в SQLite. Требования: REQ-INT-001/002, REQ-FUNC-012–013.
- **DV-02 / Composition:** `MainWindow` (Qt6 Widgets), `MarketData` (сетевой адаптер), `investlab_core/Engine.cpp` (стратегии), `Storage` (SQLite); детали физических путей уточняются при ревью исходников. Требования: REQ-FUNC-006–018.
- **DV-03 / Information:** Portfolio(id, assets, weights); Simulation(id, portfolioId, strategy, period, capital, parameters); Price(ticker, date, value); Result(simulationId, equityCurve, metrics). Это проектная логическая модель, не утверждение о созданной структуре таблиц SQLite.
- **DV-04 / Interaction:** сформировать портфель → запросить котировки → проверить покрытие выбранного периода → запустить расчёт → показать сводку → сохранить результат. При пропусках данных расчёт прекращается с именем актива и диапазоном дат (REQ-FUNC-018).
- **DV-05 / Deployment:** один процесс macOS, локальный файл SQLite, HTTPS-запросы к внешнему поставщику исторических котировок; нет сервера и брокерской интеграции.
- **DV-06 / Strategy calculation:** Buy & Hold — покупка в начале интервала; DCA — взносы по календарному расписанию; SMA/RSI — по сигналу на историческом ряду и согласованным правилам исполнения; торговые расходы — процентная комиссия. Требуется уточнить правила торговых дней и цену исполнения сигналов (см. SRS).


### 3.8 Зависимости и риски
Работы по истории котировок F02 предшествуют достоверной оценке стратегии F04/F05/F08. Риски: лимиты API, разрывы котировок и неопределённые правила торговых дат. Проверки: тесты на фиксированном наборе котировок, контроль граничных дат и независимое сравнение ручного расчёта.

## 4. Решения
- **ADR-0001:** локальный C++/Qt6/SQLite; выбор на основании ограничения macOS и отсутствия сервера.

- Решения по поставщику внешнего API и методике корректировки исторических цен остаются открытыми до проверки.

## 5. Приложения
- Требования исходного SRS: REQ-FUNC-001–018, REQ-INT-001/002, REQ-REL-001, REQ-SEC-001, REQ-PORT-001.

- Планирование: итерация — 10 рабочих дней; сроки являются учебными оценками, а не фактически затраченными днями.
- Статус: готово для обсуждения в GitHub PR; перевод в «согласовано» — после реальной фиксации ответа заказчика.
